# Peer review: CadGPT conversation continuity

**Revision:** `f4c09116a2df5b6c29082408a52f5fb9e9627d70`  
**Date:** 2026-09-29  
**Verdict:** **FAIL — release blocker for workflows that cross an MCP transport rotation**  
**Scope:** admission, Workspace Ready, fake CLI, work authority, lazy tool registration, and session recovery.

This is a replacement review record in the current checkout. The previously referenced `VERIFICATION/01a0eca8-4a42-79ed-8de8-c8374bcb578b.json` was not present here. This record is based on the supplied CR, the checked-out source, and a fresh local reproduction; it does not claim to reproduce a live AutoCAD session.

## Finding

CadGPT uses the generated MCP session ID as both transport identity and logical CadGPT conversation identity. A fresh MCP initialize creates a new UUID in `src/cadgpt/lib/mcp-session-manager.ts` and passes it to `createMcpServer`. Admission in `src/cadgpt/lib/admission.ts` and work in `src/cadgpt/lib/work-registration.ts` are keyed by that ID. A new transport/session therefore sees neither the existing claim nor work, even when the user remains in the same ChatGPT conversation.

`src/cadgpt/lib/mcp-post-routing.ts` recovers the **same** session ID and has one special headerless recovery route for `cadgpt_cad_confirm` using its private confirmation token. `cadgpt_cad_confirm` can consequently return Workspace Ready after a session change. Its work handle is then bound to the session that executed confirm. Another fresh MCP session has no automatic continuity. The only general transfer is an explicit `cadgpt_work_resume` or `cadgpt_work_start/status` call containing the old work handle. Current server instructions ask the model to perform that transfer; the runtime does not ensure it happens.

### Reproduction on the checked-out source

TypeScript was compiled to a temporary directory; all 39 emitted JavaScript files matched the existing `dist` files byte for byte. A minimal A/B state reproduction produced:

```text
A work: true; B work: false; B status: false
B work_start without continuation: CADGPT_SESSION_REQUIRED
B CAD lease with valid execution_id + authority_token: CADGPT_SESSION_REQUIRED
READY on C, work_start on D without work handle: CADGPT_SESSION_REQUIRED
Explicit work_resume to B: success
```

Using the registered control/work callbacks on B additionally produced:

```text
cg/cj: start_new_work=true, owner_id=job-authoring
next cadgpt_work_start: CADGPT_SESSION_REQUIRED
cg/status: SESSION IDLE / WORK IDLE
cg/list: CADGPT_SESSION_REQUIRED
cg/job: list text returned
```

These results establish the state-boundary defect. They do not establish the exact frequency with which the connector rotates MCP sessions in production; the user-reported test establishes that rotation occurs in the affected workflow.

## Affected workflow matrix

| Sequence after transport rotation | Current behavior / confidence |
| --- | --- |
| Workspace Ready → `cg/cj` or `cg/cl` → authoring | **Reproduced at state/callback level.** The control selector returns successfully but sees no old work; the following work start fails without continuation credentials. |
| SESSION READY, no work → `cg/cl` or `cg/cj` | **Reproduced at state level.** There is no work handle to resume; a new work start fails on the unclaimed session. |
| Workspace Ready → direct CAD call with old work handle | **Reproduced at lease level.** `acquireToolLease` checks admission before validating the handle. On a fresh server, the CAD tool may be absent altogether because its family has not been loaded. |
| `cg/list` | **Reproduced at callback level.** `prepareCadLaunch` requires admission on the new session. |
| `cg/status` / `cg/stop` | Status was reproduced as false IDLE. Source inspection shows stop looks up work by the new session, so it cannot stop the old work; its response can still print `SESSION READY`. |
| `cg/job` → `job_get` | `cg/job` is a CONTROL route and can return a list. `job_get` belongs to lazy discovery, which is not loaded on an unadmitted fresh server. |
| Lisp/Job register, import, export; development `cg/mcp` | Same FILE/development work dependency. The exact user-facing error varies with whether the relevant family is already registered. Production `cg/mcp` remains intentionally unavailable. |

## Why the green tests did not catch it

`tests/runtime-isolation.test.mjs` verifies same-ID transport recovery and explicit handle-based transfer. The rotated-session integration test calls `cadgpt_work_resume(work_handle)` **before** using a CAD tool. The `work_start/status` test injects `continuation_execution_id` and `continuation_authority_token`. The `cg/cl`/`cg/cj` state test uses one session key. None executes the reported choreography without injecting a resume step:

```text
admission → select drawing → Workspace Ready → fresh MCP session
→ cg/cj → cadgpt_work_start without continuation fields
```

The tests prove the recovery primitives work when invoked correctly. They do not prove that the connector/runtime carries continuity through a real user workflow.

## Required design boundary for Sol 5.6

1. First establish whether the actual connector supplies a trusted, stable **ChatGPT conversation identifier** or automatically propagates a private continuity capability across MCP session rotation. Inspect the request boundary with redacted diagnostics. Do not infer conversation identity from `Mcp-Session-Id`, one currently active session, user text, drawing path, or model memory.
2. If a trusted stable identifier exists, separate logical conversation state from transport state. Route a new MCP transport to the existing logical claim/workspace before control, discovery, and work dispatch. Rehydrate lazy tool families on the new server.
3. If no stable identifier exists, define an explicit, bounded continuation contract that is propagated reliably on every affected call, including READY-before-work. A work handle alone cannot cover READY-before-work. If the connector cannot propagate such a capability, seamless automatic continuity is not safely implementable; document the required user re-admission instead of guessing.
4. A valid work handle should be checked before a *transport-local* admission rejection only after the logical conversation boundary has been authenticated. Moving `assertSessionClaimed` inside `acquireToolLease` by itself is insufficient: the new server may not expose the tool, and an unscoped bearer transfer could move work into another chat.
5. Preserve explicit launch, `1 work = 1 drawing`, FILE/CAD separation, idle/stop revocation, and unrelated-chat isolation. No control command may silently wake full CAD MCP.
