## Objective
Harden the existing single-bound-drawing CadGPT, reproduce/fix the bulk Grille + Grille Tag selection failure, grow CAD MCP from the current 41-manifest-tool baseline into useful broad 2D/CAD/HVAC coverage, and improve demonstrated latency without breaking real AutoCAD workflows.

## Scope boundaries
- One source repo: thebimhouseinfo-sudo/Cadgpt. main is the sole production source of truth. Use exactly one active short-lived implementation branch per approved milestone; commit scoped changes with evidence, then review and human-gated merge to main. Never accumulate orphan branches or change a stable production capability merely to make a new gate pass.
- AutoCAD R22.0 (2018) + legacy .NET 4.6-compatible add-in remains a supported acceptance target.
- Preserve the single primary binding and no add-in idle timeout; preserve drawing anchor identity, explicit rebind, header colors, managed Jobs, SYSTEM/CAD lease separation, job result directories and user data.
- Preserve Tag ownership by two-way XData/handles; SIZE (neck size) distinct from optional FACE_SIZE and MODEL (invisible); no TAG_NUMBER-only auto-sync. Scope MEP_TAG_LINK changes so unrelated RegApp XData remains untouched. Source-code patterns are risk evidence, not proof of observed data loss.
- Do not edit TabSortV2-2.lsp. Change only proven Grille/Grille Tag-related Lisp faults; do not mass-refactor the TBH Toolkit.
- Do not clone the entire AutoCAD API, expose arbitrary command strings, or grant unrestricted Python shell access. No speculative rewrites of transport or add-in.
- This plan is not an instruction to manipulate a production DWG. Live E2E requires a disposable copy and user-controlled host. No default use of an active drawing as a QA fixture, even when an AutoCAD session is bound.
- Drawing identity and AppData metadata can carry lasting state: acceptance/rollback must snapshot both test DWG bytes and test Drawing Anchor/result metadata. Never restore a production Anchor from a fixture, never reuse a fixture Anchor with a live production drawing.
- The internal AutoCAD R22.0/.NET Framework 4.6 add-in is operational; no .NET bridge is presumed available. Require an explicit spike with real editor UI-thread and DocumentLock proof before choosing that route.
- Every accepted capability must have a named engineering consumer scenario and one observed end-to-end postcondition, not just a schema entry.

This roadmap contains separate finite implementation Jobs, not a single mega-Job. Work serially on exactly one active milestone branch (for example work/cadgpt-m0a), branched from latest main. Within it, commits can close finite Job Packs independently. Complete review and applicable host tests, obtain Human approval and merge only that accepted milestone into main. Archive/delete the already merged branch; create the NEXT milestone branch afresh from updated main. Do NOT reset/rebase a branch carrying future unmerged changes and do not mix multiple milestone packs before the prior release gate. Stage new write families behind explicit rollout gates, default-off until accepted. Never merge failing/unverified changes. If main advances meanwhile, reconcile intentionally with a reviewed diff and rerun tests; never force-push/reset unrelated work.

- J03C0 DURABLE JOURNAL BOOTSTRAP & LOSS DETECTION (mandatory BEFORE J03C1 and any v2 creating tool):
  - Introduce a versioned CadGPT journal-registration marker in the drawing Named Objects Dictionary (distinct from the existing Drawing Anchor) with journal schema, stable journal_instance_id/epoch and a registration fingerprint; pair it with a durable drawing-owned AppData journal header and an independently maintained authorized per-host registry/index. Compare marker, anchor, instance/epoch and sidecar identity before admitting writes. A valid existing Drawing Anchor ALONE does not prove the journal has never existed. An epoch is an immutable identity of ONE adoption lifetime, never just a display label or authorization credential.
  - Journal bootstrap is a controlled two-phase REGISTRATION (not two CAD mutation RPCs): authorization and identity check → reserve/register an INIT_PENDING record outside the per-drawing journal → create/read back DWG marker → write/read back matching AppData header → confirm registration marker is durable in a saved/reopened disposable DWG (explicit user-approved save only) → mark READY. Failure or interrupted initial save remains BOOTSTRAP_INCOMPLETE / UNKNOWN_PROVENANCE; no v2 write admitted. Do not auto-save a live production DWG. Ordinary later user-driven DWG saves follow the separate J03C-SAVE contract and do NOT rerun registration.
  - Decision matrix: matching DWG marker + sidecar + host index + epoch-bound operation-integrity sequence and J03C-SAVE checkpoint invariants => READY; an **older last_saved_checkpoint in the file** than latest_operation_checkpoint in live AppData is ALLOWED only when supported by current unsaved drawing/session evidence and consistent journal records, never an automatic mismatch. Marker present but sidecar missing/corrupt, wrong epoch or restored prior history => JOURNAL_LOST/IDENTITY_CONFLICT; sidecar/index exists but marker missing => BOOTSTRAP_INCOMPLETE/DWG_ROLLBACK; missing reservation/index entries despite matching header => JOURNAL_INCOMPLETE; none of marker/sidecar/index => UNKNOWN_PROVENANCE, not proof of a virgin DWG. New DWG provisioning requires trusted creation evidence; other drawings require user-approved adoption with backup and inventory. Adoption creates a NEW epoch with history/tombstone for the retired epoch. No old-epoch intent is replayable after adoption.
  - EPOCH-LINK INVARIANT: J03C-CLIENT and interactive v2 callers must persist the original journal_instance_id/epoch and anchor with operation_id, immutable request and authorization context BEFORE dispatch. The server must record the same epoch in both operation reservation/index and journal record, and compare it to the trusted DWG marker, AppData header and host registry on every first call, lookup, retry, reconnect, and resumed delegated Job. Epoch is not an alternate operation primary key; the stable operation_id cannot gain permission to execute by switching epochs. If the caller's original intent epoch differs from current marker/header/journal epoch, return JOURNAL_EPOCH_CONFLICT **before any COM**, regardless of an empty new journal. Never silently rebind an old intent to an adopted journal. A deliberate user-authorized NEW creation after adoption must have a NEW action intent and NEW operation_id, with an explicitly captured current epoch.
  - OPERATION-LEDGER INTEGRITY: Beyond matching headers, maintain a separately persisted, append-only admission/reservation manifest keyed by anchor+epoch+operation_id (no operation kind in primary identity), storing monotonically increasing sequence/issuance checkpoint, server hash, durable owner/action key, dispatch fence/state and expected journal-record identifier. Mirror an epoch-specific high-water sequence + rolling integrity digest/checkpoint in the AppData journal header and independent host registry; on supported, user-approved DWG saves record the related checkpoint/fingerprint in the DWG marker. On process start/reopen/rebind and before NEW operation admission or replay, reconcile the manifest's known operation IDs/high-water sequence/checkpoint with journal records, caller dispatch ledgers, marker/header/host index and accessible created-handle evidence. A chain/digest detects accidental gaps, not malicious rollback when ALL trusted stores roll back in lockstep; do not claim cryptographic tamper-proof or cross-machine exactly-once.
  - REQUIRED DISPATCH FENCE: follow J03C-EXEC ONE-CALL RPC ordering exactly. The caller writes/readbacks intent and marks DISPATCH_POSSIBLE **before** sending ONE mutation call; only INSIDE that call does the server validate and persist reservation/manifest, journal and IN_PROGRESS before COM. A crash or lost response may become UNKNOWN_OUTCOME; missing reservation after caller DISPATCH_POSSIBLE is NOT proof no request arrived and never triggers blind retry. A caller INTENT_PREPARED with proven no dispatch may issue the FIRST call when J03C0/SAVE integrity checks pass. Missing/invalid manifest or sequence/checkpoint freezes new v2 writes pending reconciliation. No undocumented prepare→execute pair.
  - RESTORE COUNTEREXAMPLE: rollback only the operation journal to before COPY while retaining the already changed DWG and caller IN_FLIGHT, marker/header epoch, and independent reservation manifest. The tool MUST detect missing COPY operation ID, return UNKNOWN_OUTCOME/JOURNAL_INCOMPLETE, inspect created handles for reconciliation, and perform ZERO new COM copies. Likewise journal record COMMITTED with missing/erased handles is not a new intent. No automatically generated replacement ID, synthetic row or reset high-water mark can clear the uncertainty.
  - Physical limitation: DWG metadata, per-drawing AppData and even host registry can all be lost/restored together. No purely local test can prove that such a drawing has never had a journal. When full history is unavailable, flag UNKNOWN_PROVENANCE, disable automatic recovery of old operations, and require explicit manual reconciliation; a user-authorized *new* intent after controlled adoption is distinct from retrying a missing old operation. Do not claim exactly-once under total metadata loss.
  - Test new managed DWG, old drawing without marker, marker-only, sidecar-only, index-only, stale epoch, partial bootstrap crash, unsaved marker, DWG backup restore, AppData deletion, machine migration, copied DWG with duplicated anchor/marker, and all metadata lost. Add J03C integrity tests for matching marker/header/epoch but missing one operation record, restored journal with lower sequence/checkpoint, manifest-only prior dispatch, tampered/missing ledger digest, caller IN_FLIGHT vs INTENT_PREPARED, and old-epoch intent submitted after controlled adoption. Each ambiguous case must fail closed for uncertain old operations. Legacy read/tools and manual workflows are not blanket-blocked by an unfinished v2 journal rollout.
- J03C-SAVE SAVED vs LIVE CHECKPOINT SEMANTICS (applies to J03C0/1, no implicit Save):
  - Persist distinct counters per epoch: `latest_operation_checkpoint` = monotonic AppData/host-index operation reservation/readback progress; `last_saved_checkpoint` = checkpoint whose **DRAWING CONTENT** is verified saved in the DWG file (alongside saved drawing fingerprint/generation, anchor and epoch). Maintain `live_document_generation`/unsaved-dirty evidence only for the currently verified open AutoCAD document. A registration marker/epoch may be persisted while a newer sequence of CAD changes is not saved. Compare these values for provenance, never require equality under ordinary active unsaved edits.
  - Use save-aware host observation and bounded R22.0 feasibility test: identify actual Save/SaveAs success, pre-save snapshot, write/checkpoint ordering and readback of persisted DWG. Record last_saved_checkpoint only after verified completed Save of that precise DWG identity/generation; an event, file timestamp or dirty flag alone does not prove durable contents. If an in-process AutoCAD save event/COM synchronization or safe file readback cannot be proven, treat persistence as UNVERIFIED_SAVE, retain previous last_saved_checkpoint and never auto-save just to satisfy journal metadata. Checkpoint marker update must occur BEFORE the user-authorized Save that persists it, or remain a pending checkpoint; a post-Save unsaved marker edit cannot retroactively certify saved bytes. SaveAs changing drawing identity/anchor follows separate J03C0 adoption/identity guard, not a blind checkpoint transfer.
  - A successful create/modify COM call with handle readback may return `COMMITTED` for the **current live document** with `durability: LIVE_UNSAVED` when latest_operation_checkpoint exceeds last_saved_checkpoint or Save evidence is unavailable. Report `durability: SAVED_VERIFIED` only for an operation proven present in the persisted DWG at or beyond its checkpoint. The returned `COMMITTED/LIVE_UNSAVED` is not a promise that bytes survive AutoCAD termination. On reopen/restart, cached COMMITTED does not imply current success: first compare saved file generation, content/handle readback and journal/intent history. If a previously created handle is absent because unsaved changes were lost (or indistinguishable from later ERASE/UNDO), return `DWG_UNSAVED_ROLLBACK/UNKNOWN_OUTCOME`, NEVER cached success or automatic COPY replay. If after-reopen saved data contains expected object, reverify before reporting SAVED_VERIFIED.
  - State table: OPEN+DIRTY and `last_saved_checkpoint=10, latest_operation_checkpoint=15` with matching live handles/journal => VALID_LIVE_UNSAVED, not JOURNAL_INCOMPLETE. Successful verified Save of checkpoint 15 => SAVED_VERIFIED at 15; failed/aborted Save => persisted checkpoint remains 10. Crash/reopen from checkpoint 10 with AppData/index at 15 => UNSAVED_ROLLBACK/UNKNOWN_OUTCOME, frozen automatic retry for affected operations; do not lower sidecar high-water or silently delete journal. Saved file at 15 but journal restored to 10 => JOURNAL_INCOMPLETE (as J03C0 requires), not safe to re-create.
  - Negative controls: 10→15 unsaved healthy live session, verify Save success, Save initiated but fails, SaveAs into new path/anchor, marker updated after Save but not actually persisted, AutoCAD crash before Save, reopen 10 with journal 15, reopen 15 with journal 10, user ERASE/UNDO on current session, reopened document with lost/erased handle and missing save observer. Compare actual content/handles and call count, not counters alone. No extra COM creation occurs on any ambiguous recovery; no compulsory AutoCAD Save, fake saved-state claim or blanket stoppage of harmless live unsaved changes.
- J03C-EXEC ONE-CALL MUTATION RPC (single command transport, NOT prepare→execute):
  - Authoritative order: (1) caller retrieves authorized READY epoch + stable original action context via read-only lookup; (2) caller persists immutable intent+operation_id+epoch as INTENT_PREPARED; (3) caller durably marks DISPATCH_POSSIBLE before any network send; (4) caller sends exactly ONE named CAD MCP v2 mutation request, or the identical policy-guarded manifest gateway equivalent, with same ID/epoch/request; (5) server IN THAT RPC validates current drawing/lease/owner/epoch, saved/live provenance and policy, then acquires per-operation/CAD host locks, checks journal and independently persisted reservation history; (6) server atomically reserves id in admission ledger and records PREPARED then IN_PROGRESS/dispatch fence with durable readback BEFORE COM; (7) server executes COM ONCE, reads back handles and records result/COMMITTED with live/save durability flag. No separate mutating prepare RPC or implicit retry; server-owned reservation and COM never occur before the caller's dispatch request.
  - Crash boundaries: after INTENT_PREPARED but before DISPATCH_POSSIBLE and with provable non-dispatch => first invocation may be admitted; after DISPATCH_POSSIBLE but before request arrival, caller cannot prove no dispatch, so UNKNOWN_OUTCOME and no automatic new request without a bounded read-only reconciliation; after server reservation but before COM => server may certify no-effect ONLY with verified execution-fence/host evidence, otherwise UNKNOWN_OUTCOME; after COM before result/response => reconcile handles and independent record, never repeat COM; after SAVE/reopen => J03C-SAVE readback rules. A missing server row for caller DISPATCH_POSSIBLE is NOT permission to create again. Fresh deliberate user intent is distinct, gets a NEW ID/epoch.
  - Named `cad__*` and `cad_invoke_manifest_tool` route through one J03B authority and the same J03C-EXEC admission/journal logic. Read-only `get_operation_status` may exist for authorized reconciliation but is NEVER a hidden mutating prepare endpoint. Current runtime is one-call upstream; migration must use versioned v2 without modifying legacy public schema. Mutation host lock covers all server journal/COM critical steps; filesystem writes and host action have separate durability, not an invented atomic transaction.
  - Mandatory fault injection with event/sequence tracing: crash BEFORE and AFTER each of steps 2–7; caller marks DISPATCH_POSSIBLE but send fails; server receives twice concurrently via named+gateway; reservation persisted but COM not started; COM done with lost response; Save failed/aborted; Save succeeds while journal AppData update pending. No second COPY/MIRROR for same intent in any retry case. Reviewer checks exact ordered event logs, durable state snapshots, operation count and negative controls, not only mock status codes.

  - Persist schema_version, journal_instance_id/epoch, kind, server-computed payload hash, original source preconditions, owner/action scope, reservation sequence/checkpoint, live_document_generation, last_saved_checkpoint/latest_operation_checkpoint and audit execution/lifetime IDs; states PREPARED -> IN_PROGRESS -> COMMITTED/FAILED/UNKNOWN_OUTCOME with separate durability LIVE_UNSAVED/SAVED_VERIFIED and per-handle readback. Under host/operation locks inside J03C-EXEC, persist ledger/journal/IN_PROGRESS before COM and reconcile after crash/partial result. A COM success without journal COMMITTED is UNKNOWN_OUTCOME until independently verified. Cached COMMITTED requires epoch/integrity/handle readback and current saved/live durability validation: a prior LIVE_UNSAVED success cannot be replayed as persisted success after reopen. Sidecar and DWG are not atomic; no exactly-once or auto Save.
- J03C-CLIENT DURABLE CALLER INTENT (mandatory BEFORE dispatch from Job orchestration):
  - The managed Job orchestrator owns intent creation, never the COM tool or model-generated retry text. Resolve immutable Job task/action checkpoint key (Job identity + task/node/action sequence + anchor + intent revision), read authorized J03C0 READY epoch, atomically persist one operation_id + original epoch, kind, effective request, owner scope and INTENT_PREPARED in AppData.
