# CadGPT AppData

CadGPT keeps user/runtime-generated data separate from installation source.

## Beta location

During Beta, the app-data root is intentionally inside the repository:

```text
appdata/
```

Runtime code resolves it through `CADGPT_APPDATA_ROOT` / the shared appdata helper rather than hard-coding the repository path.

For a packaged build, the same virtual `appdata/...` paths can move to a per-user location such as:

```text
%LOCALAPPDATA%\CadGPT\
```

without changing capability logic or ChatGPT-facing paths.

## Layout

```text
appdata/
├── data/
│   └── runs/             persistent outputs/evidence generated by runs
├── lisp-draft/           AutoLISP workbench; not part of the permanent library
├── runtime/
│   └── dynamic-lisp/     temporary AI-derived/parameterized AutoLISP variants
├── state/                background-agent/runtime state
└── logs/                 local runtime logs
```

`dynamic-lisp` is a runtime-storage name, not a separate Lisp type. Every artifact there is still ordinary AutoLISP/Visual LISP source; it is called dynamic only because CadGPT/AI derived it from a registered source using bounded runtime parameters.

## Persistence rules

- `data/**` — persistent user-generated run data; not source control.
- `lisp-draft/**` — persistent across CadGPT sessions while a Lisp is being developed/tested; not discoverable as a permanent Lisp capability.
- `runtime/**` — disposable runtime artifacts; may be recreated.
- `state/**` — internal process state; may be recreated unless explicitly documented otherwise.
- `logs/**` — diagnostic logs; may be rotated/deleted.

Only this README is committed. Generated AppData contents are ignored by Git.

General file tools expose only:

```text
appdata/data/**
appdata/lisp-draft/**
```

`runtime/**`, `state/**`, and `logs/**` are internal CadGPT areas rather than generic model-editable filesystem roots.

## Lisp promotion

A new or substantially changed Lisp should normally live in `appdata/lisp-draft/**` while it is being authored and tested.

After the applicable static/load/runtime gates pass, promote it into permanent `lisp/**` with `lisp_promote_draft`. Promotion re-validates the source and updates `registry/lisp-registry.json` together with the permanent file. The operation rolls the permanent file back if the registry update fails.

Registry `ai_mode` describes how AI may use a permanent source (`static` as-is or `dynamic` with bounded runtime adaptation). It does not define a different source-file type.

AI-derived runtime variants stay under `appdata/runtime/dynamic-lisp/**`. They remain temporary artifacts unless the user explicitly decides that a resulting source change should become a reusable permanent capability through the normal draft/promotion workflow.
