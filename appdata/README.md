# CadGPT AppData

CadGPT keeps user/runtime-generated data separate from installation source.

## Beta location

During Beta, the app-data root is intentionally inside the repository:

```text
appdata/
```

Runtime code must resolve it through `CADGPT_APPDATA_ROOT` / the shared appdata helper rather than hard-coding the repository path.

For a packaged build, the same virtual `appdata/...` paths can move to a per-user location such as:

```text
%LOCALAPPDATA%\CadGPT\
```

without changing capability logic.

## Layout

```text
appdata/
├── data/
│   └── runs/             persistent outputs/evidence generated by runs
├── lisp-draft/           AutoLISP workbench; not part of the permanent library
├── runtime/
│   └── dynamic-lisp/     ephemeral parameterized/generated Lisp artifacts
├── state/                background-agent/runtime state
└── logs/                 local runtime logs
```

## Persistence rules

- `data/**` — persistent user-generated run data; not source control.
- `lisp-draft/**` — persistent across CadGPT sessions while a Lisp is being developed/tested; not discoverable as a permanent Lisp capability.
- `runtime/**` — disposable runtime artifacts; may be recreated.
- `state/**` — internal process state; may be recreated unless explicitly documented otherwise.
- `logs/**` — diagnostic logs; may be rotated/deleted.

Only this README is committed. Generated AppData contents are ignored by Git.

## Lisp promotion

A new or substantially changed Lisp should normally live in `appdata/lisp-draft/**` while it is being authored and tested.

After the applicable static/load/runtime gates pass, promote it into permanent `lisp/**`. Promotion must update `registry/lisp-registry.json` in the same workflow so permanent library source and semantic discovery metadata cannot drift.
