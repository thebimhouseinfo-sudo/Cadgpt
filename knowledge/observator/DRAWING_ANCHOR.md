# Drawing Anchor Contract

## Purpose

The Drawing Anchor is the minimal persistent identity marker owned by Observator inside a DWG.

It exists only after Observator first needs persistent metadata for that drawing. Opening a drawing in CadGPT alone does not create one.

The anchor is not proof that AutoCAD saved the latest drawing state to disk. It carries the logical drawing identity and the Observation revision from which that DWG copy is currently continuing.

## Lazy creation

```text
first Observation Job needing persistence
→ no anchor found
→ build drawing_id from current drawing name + creation time/date timestamp
→ initialize last_revision
→ insert Drawing Anchor
→ create AppData/drawings/<drawing_id>/
→ continue Job
```

`drawing_id` is created once. Rename, move, copy, or Save As must not regenerate it.

## Ownership and mutation rule

The Drawing Anchor is the only CAD database object Observator may create or modify.

Observator may not use this exception to mutate business geometry, tags, numbering, layers, properties, or other user drawing content.

## Minimal payload

The anchor intentionally stores only:

```text
drawing_id
last_revision
```

Field meaning:

- `drawing_id` — stable unique id generated by CadGPT and used as the AppData key. It embeds the drawing name at first anchor creation plus the local creation timestamp.
- `last_revision` — hierarchical Observation revision label carried by this DWG copy and used as the parent/checkpoint for the next Observation Job.

V1 `drawing_id` format:

```text
<origin-name>-<HHMMSS>-<DDMMYY>
```

Example:

```text
Bowhotel-143527-100826
```

The `HHMMSS` + `DDMMYY` segments are the anchor creation timestamp in local system time. Including seconds keeps the id compact while making accidental collisions extremely unlikely for practical CadGPT use. No separate random suffix is required by V1.

The creation time/date and origin drawing name are not stored as separate anchor fields. They are immutable provenance embedded once in `drawing_id`.

Rename, move, copy, or Save As never regenerate `drawing_id`.

The anchor must not store:

- a separate current/origin drawing-name field;
- a separate creation-time field;
- name history;
- fingerprint/version GUID history;
- file paths;
- branch history;
- parent revision history;
- system membership;
- equipment/duct/grille semantics;
- entity snapshots;
- Job-specific business state;
- duplicated AppData metadata.

## Logical identity

`drawing_id` is authoritative for CadGPT metadata identity.

Example:

```text
first observed file: Bowhotel.dwg
created at: 14:35:27 on 10/08/2026
created drawing_id: Bowhotel-143527-100826

later rename: BOWHOTEL-MEP-CLIENT.dwg
later copy: CLIENT-COMMENT.dwg

anchor drawing_id remains:
Bowhotel-143527-100826
```

Therefore:

```text
copy / rename / move / Save As
→ anchor travels with DWG
→ same drawing_id
→ same logical drawing
```

## Revision meaning

`last_revision` is not a global "latest wins" pointer. It identifies the Observation revision from which this particular DWG copy is continuing.

Revision labels are **hierarchical strings**, never numbers or floating-point values.

Branch segments use two-digit zero padding:

```text
12.01
12.02
...
12.09
12.10
```

If a branch itself branches again, the same rule applies recursively:

```text
12.01.01
12.01.02
```

Zero padding is part of the stored label and must be preserved exactly. `12.01`, `12.10`, and `12.01.01` are strings, not decimal numbers.

Example:

```text
opened DWG anchor.last_revision = 12
AppData contains mainline revisions through 15
```

The opened DWG may simply be an older copy. If the user continues working from it, the next Observation Job creates revision `12.01` rather than silently adopting revision `15`.

Conceptually:

```text
10 → 11 → 12 → 13 → 14 → 15
           \
            → 12.01
```

Revision `12.01` is new work continued from revision `12`. Revisions `13–15` remain valid history on another branch of the same logical drawing lineage.

The branch relationship belongs in AppData revision metadata:

```text
revision: "12.01"
parent_revision: "12"
```

It does not require adding branch metadata to the Drawing Anchor. The anchor only needs to point to the current DWG copy's `last_revision`.

Further revision labels extend the hierarchy using the same two-digit branch segment convention. The exact allocation rule belongs to the AppData revision allocator; the authoritative parent relationship remains `parent_revision` metadata rather than inference from string formatting alone.

## Per-Job update rule

Every successfully completed Observation Job performs this sequence:

```text
parent = anchor.last_revision
→ Job observation behavior
→ allocate a new hierarchical revision label in AppData
→ store parent_revision = parent
→ write/finalize Job-selected AppData/log records
→ update anchor.last_revision to the new revision exactly once
→ Job complete
```

The new revision label must be unique within that `drawing_id`. It must not be derived by numeric arithmetic on `last_revision` because revision labels are strings and the history may already contain another branch.

The update belongs to Observator itself. It must not be delegated to application shutdown, AutoCAD save events, cache flushing, process cleanup, or another background engine.

There is no additional `Save()` requirement. Observator does not try to certify whether AutoCAD persisted the current in-memory drawing to disk.

## Crash and reopen semantics

If AutoCAD terminates before the final anchor update, the DWG copy may retain its previous `last_revision` while AppData may contain partial or newer records.

If AutoCAD terminates after the anchor update but before a DWG save, the file on disk may still contain the previous anchor value. This is expected.

When an older DWG copy is intentionally opened, its anchor revision is accepted as the branch point/current checkpoint carried by that copy. Newer AppData must not automatically overwrite or advance it.

## Physical representation

The physical AutoCAD representation is a separate implementation choice. It should be non-graphical and resistant to normal accidental delete/purge operations. The logical payload above is the authoritative contract.
