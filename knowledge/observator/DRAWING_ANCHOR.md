# Drawing Anchor Contract

## Purpose

The Drawing Anchor is the minimal persistent identity marker owned by Observator inside a DWG.

It exists only after Observator first needs persistent metadata for that drawing. Opening a drawing in CadGPT alone does not create one.

The anchor is not proof that AutoCAD saved the latest drawing state to disk. It carries the logical drawing identity and the Observation revision present in that DWG copy.

## Lazy creation

```text
first Observation Job needing persistence
→ no anchor found
→ generate CadGPT drawing_id
→ capture origin_name
→ set created_at
→ initialize last_revision
→ insert Drawing Anchor
→ create AppData/drawings/<drawing_id>/
→ continue Job
```

## Ownership and mutation rule

The Drawing Anchor is the only CAD database object Observator may create or modify.

Observator may not use this exception to mutate business geometry, tags, numbering, layers, properties, or other user drawing content.

## Minimal payload

The anchor intentionally stores only:

```text
drawing_id
origin_name
created_at
last_revision
```

Field meaning:

- `drawing_id` — stable unique id generated by CadGPT. This is the logical drawing identity and AppData key.
- `origin_name` — drawing name captured when the anchor is first created. It is immutable provenance, not the current file name.
- `created_at` — timestamp when CadGPT first created this drawing identity/anchor. It is immutable provenance.
- `last_revision` — monotonically increasing Observation revision carried by this DWG copy. It is updated once after each successfully completed Observation Job.

`origin_name`, `created_at`, and `drawing_id` never change because of rename, copy, move, or Save As.

The anchor must not store:

- name history;
- fingerprint/version GUID history;
- file paths;
- system membership;
- equipment/duct/grille semantics;
- entity snapshots;
- Job-specific business state;
- duplicated AppData metadata.

## Logical identity

`drawing_id` is authoritative for CadGPT metadata identity.

`origin_name` and `created_at` are lightweight provenance only. They help a human or recovery routine recognize where the CadGPT identity originated, but they are not hard gates that invalidate a drawing after rename/copy/Save As.

Therefore:

```text
copy / rename / Save As
→ anchor travels with DWG
→ same drawing_id
→ same logical drawing
```

## Revision meaning

`last_revision` lets Observator compare the DWG copy being opened with the Observation history stored under the same `drawing_id`.

Example:

```text
opened DWG anchor.last_revision = 12
AppData latest revision          = 15
```

This means only that the opened DWG copy carries Observation checkpoint 12 while later Observation records exist in AppData.

It does **not** mean the DWG is wrong, stale, corrupt, or should automatically be advanced to revision 15. The user may intentionally have opened an older copy.

Likewise, two copied DWGs may carry the same `drawing_id` and different `last_revision` values. They are different versions/copies of the same logical drawing lineage.

## Per-Job update rule

Every successfully completed Observation Job performs this sequence:

```text
Job observation behavior
→ write/finalize Job-selected AppData/log records for revision N+1
→ update anchor.last_revision from N to N+1 exactly once
→ Job complete
```

The update belongs to Observator itself. It must not be delegated to application shutdown, AutoCAD save events, cache flushing, process cleanup, or another background engine.

There is no additional `Save()` requirement. Observator does not try to certify whether AutoCAD persisted the current in-memory drawing to disk.

## Crash and reopen semantics

If AutoCAD terminates before the final anchor update, the DWG copy may retain revision N while AppData may contain partial or newer records for N+1.

If AutoCAD terminates after the anchor update but before a DWG save, the file on disk may still contain revision N. This is expected.

When an older DWG copy is intentionally opened, its anchor revision is accepted as the Observation checkpoint carried by that copy. Newer AppData must not automatically overwrite or advance it.

## Physical representation

The physical AutoCAD representation is a separate implementation choice. It should be non-graphical and resistant to normal accidental delete/purge operations. The logical payload above is the authoritative contract.
